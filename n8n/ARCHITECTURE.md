# AI Chief · n8n multi-user architecture (P2.1)

## Principle

FastAPI is the single authority for identity and authorization. n8n is a
thin orchestrator of HTTP calls against that API. n8n **never** decides which
user's data it is processing, and **never** submits a numeric `user_id` that
FastAPI would blindly trust.

## Identity model

- Each end user connects their Gmail through the app's own OAuth flow into a
  `user_integrations` row (`provider="google"`, `status="active"`,
  `account_id` = the Gmail address). This is the **trusted server-side
  mapping** between an account and a user — it is created by OAuth, which n8n
  cannot forge.
- n8n workflows identify work by `account_id` **only**. FastAPI resolves it
  with `resolve_ingest_user`:
  - `account_id` alone → exactly one active Google integration (404 unknown,
    409 ambiguous if two integrations share the account, 403/active-checks
    otherwise);
  - `user_id` + `account_id` → must agree (403 mismatch);
  - `user_id` only → active user + active Google integration;
  - neither → legacy single-user owner fallback, kept only as the original
    key-gated contract (the POC path). Member mail cannot silently land under
    the owner because a supplied `account_id` always resolves to its owner.

## Credential selection (Gmail)

- Gmail OAuth tokens live **only** in the backend (per-user rows) and are
  refreshed by `google_auth`/`gmail_service`. n8n holds **no Gmail
  credential**.
- Why: this n8n deployment has a single global credential store with no
  dynamic per-execution credential selection and no OAuth-consent table. A
  shared `gmailOAuth2` node would query one mailbox for everyone (the old
  `ai-chief-email-sync.json` design) — that pattern is retired.
- Consequence: Gmail fetching is backend-native
  (`gmail_service.sync_emails(max_results, db, user_id=…)`), invoked per user
  through the agent endpoint below.

## Execution flow

```
User connects Gmail  →  user_integrations (google, active, account_id)
n8n (any trigger)     →  GET /api/integrations/agent/accounts   (ingest key)
                      →  for each account:
                          POST /api/integrations/agent/sync
                             { account_id, limit, auto_process }
FastAPI               →  resolve account → user (trusted mapping)
                      →  sync with THAT user's own stored Gmail creds
                      →  rows stamped user_id = resolved user
                      →  local Ollama analysis enqueued per inserted email
```

A new user is onboarded automatically: after connecting Gmail in Settings,
their `account_id` appears in `/accounts` and the next scheduled sync covers it.

## Server-to-server endpoints

| Endpoint | Auth | Purpose |
|----------|------|---------|
| `GET /api/integrations/agent/accounts` | ingest key (`X-API-Key`) | Trusted account enumeration; excludes revoked/inactive |
| `POST /api/integrations/agent/sync` | ingest key | Per-account sync under the owner of that account |
| `POST /api/integrations/emails/ingest` | ingest key | Idempotent batch insert (P1), identity per rules above |

The ingest key is a server secret held by the n8n container; it is not a
bypass because every request still resolves identity from server state and
validates accounts/integrations. The only private APIs (`/api/emails`, etc.)
remain user-JWT-scoped.

## Workflow classification

| Workflow | Class | Reason |
|----------|-------|--------|
| `ai-chief-email-sync.json` (multi-user sync) | MULTI-USER | account-driven, backend resolves identity |
| `ai-chief-phase2-monitor.json` | SINGLE-USER (owner) | read-only owner monitor |
| WhatsApp Inbound | SINGLE-USER (owner) | Twilio org number → owner; Twilio HMAC verified server-side |
| `ai-chief-phase1-ingest-poc.json` | UNUSED-LEGACY | manual POC, inactive |

## n8n trust boundary (documented limitation)

- n8n may choose *which account* to operate on, but only among accounts the
  backend reports; it cannot invent a user, and a mismatch is rejected.
- n8n cannot host per-user Gmail OAuth credentials in this deployment (single
  global store). Gmail access therefore stays backend-native; n8n's role is
  orchestration + reporting.
- All output of the sync workflow is generated by the backend; no secrets are
  stored in workflow files or Code nodes.
